不是继续扩展 LOB，不是立刻做 maker，也不是先用 shadow PnL 选择策略。

准确顺序应当是：

```text

        ↓

        ↓

        ↓

        ↓

        ↓
```

```text

B. micro-live actual result
C. delayed OrderFilled-only ex-self prediction
```

# 二、补全真实订单“真相链”

你的当前缺口不是 paper fill，而是：

```text
数据库中真实订单状态事件 = 0
```

下一阶段必须建立如下真相层级。

## 1. A：模拟盘预测

在提交真实订单之前，先冻结预测结果：

```text
predicted_status
predicted_filled_size
predicted_avg_price
predicted_fee
predicted_levels_consumed
predicted_arrival_ts
predicted_book_hash
predicted_book_generation
predicted_latency_ms
prediction_model_version
```

注意顺序必须是：

```text
先产生并持久化预测
再允许真实提交
```

不能在看到真实成交以后重新计算预测。

---

## 2. B：真实订单生命周期

真实结果不能只看 `POST /order` 的 HTTP 返回。

Polymarket 的订单可能处于：

```text
live
matched
delayed
unmatched
```

交易结算还会继续经历：

```text
MATCHED
MINED
CONFIRMED
RETRYING
FAILED
```

User WebSocket 会发布用户订单的 placement、update、cancellation，以及交易的 MATCHED、MINED、CONFIRMED、RETRYING、FAILED 变化。([Polymarket Documentation][4])

因此要区分两种真实结果：

```text
actual_execution_truth:
    MATCHED 时确定成交价格、成交量和 taker/maker 身份

actual_ledger_truth:
    CONFIRMED 后才最终记入已确认真实账本
```

不能将：

```text
HTTP success
或 MATCHED
```

直接当成最终链上成功。

一个 2026 年的近期预印本还专门研究了 off-chain match 后 on-chain settlement 失败的“ghost fill”问题。该论文不是官方规则说明，但进一步说明 MATCHED 与最终 CONFIRMED 必须分开记录；官方订单生命周期本身也已经提供 RETRYING 和 FAILED 状态。([arXiv][5])

---

## 3. C：Delayed OrderFilled ex-self

事后再运行一次 OrderFilled-only 预测，并排除：

```text
probe wallet
funder address
orderID / order hash
tradeID
transaction hash
maker order IDs
```

2026 年一篇基于 Polymarket V1 时期数据的微观结构研究，将约 300 亿条公开 WebSocket 事件与链上 `OrderFilled` 对齐后发现，公开 feed 推断的成交方向与链上结果只约 59% 一致。这个精确比例不能直接假设对当前 V2 仍然不变，但它充分支持一个工程原则：**成交方向、身份和最终成交归属应该以链上 truth 为准，而不是仅靠盘口变化推断。** ([arXiv][6])

# 六、Phase 5B：先跑 50～100 次 no-submit

你目前只有一次 no-submit，不足以证明生产控制面可靠。

每次 no-submit 都执行完整流程：

```text
选 market
→ 风控
→ 读取 market-specific 参数
→ 冻结预测
→ 构造并签名订单
→ 计算 order hash
→ 不发送
→ 保存所有 artifact
→ 生成 reconciliation manifest
```

no-submit 验收：

```text
100% 有 OrderIntent
100% 有 BookState/hash/generation
100% 有 fee/tick/min-size/delay metadata
100% 有签名订单和 order hash
100% 风险配置可追溯
0 次真实 HTTP order submit
0 次秘密信息进入日志
同一输入可重复生成一致的预测
```

直到连续多轮 no-submit 都通过，才能把：

```yaml
live_probe_enabled: false
```

切换为受控 live 模式。

# 七、Phase 5C：10～20 笔机械化真实验证

第一批不是验证策略，而是验证交易机制。

## 第一批 market 选择

只选择：

```text
LOB quality = REDUNDANT
双路 feed 一致
REST book 与本地 book 一致
高流动性
非 sports
非 itode 250ms delay
非临近关闭或结算
tick/min-size/fee 信息完整
User WS 已连接
当前没有自己的 open order
```

Polymarket 某些 crypto/finance 市场可能有 250ms taker delay，部分 sports market 使用配置化 delay；当前下单文档还说明 sports marketable order 通常有 1 秒 placement delay，且开赛时 resting order 会被自动清除。因此延迟市场必须独立校准，不能和普通市场混在第一批里。([Polymarket Documentation][9])

## 推荐机械用例

| 用例                | 预测目标           | 重点                |
| ----------------- | -------------- | ----------------- |
| FOK BUY，极小 size   | FULL           | 基础 full-fill      |
| FOK BUY，超过可见合格深度  | REJECT/NO FILL | false-positive 检验 |
| FAK BUY，小于可见深度    | FULL           | 价格与手续费            |
| FAK BUY，接近或略超可见深度 | PARTIAL        | 部分成交              |
| FOK SELL          | FULL 或 REJECT  | SELL 语义           |
| FAK SELL          | FULL/PARTIAL   | 双向检验              |

SELL 只能使用账户真实持有的 outcome token，不能假设可以裸卖。

还要特别核对输入语义：官方文档中，FOK/FAK 的 BUY 数量表示想花费的美元金额，而 SELL 表示卖出的 share 数量。这个区别很容易造成 paper engine 与真实 API 的数量不一致。([Polymarket Documentation][4])

## 第一批停止条件

下面任意一项出现，立即停止后续 probe：

```text
模拟 FULL、实际无成交
模拟 REJECT、实际成交
实际成交超过模拟预测上界
手续费无法解释
orderID 无法和 user WS 对上
HTTP 超时后无法确认订单是否存在
账户余额变化无法用成交和手续费重建
出现未归属 open order
出现自成交
kill switch 或 cancel-all 失败
```

# 九、不要拿全部样本同时拟合和验收

建议按 market/event/day 分组，而不是逐笔随机拆分：

```text
训练集：70%
验证集：15%
最终 holdout：15%
```

例如：

```text
同一个 condition_id 的 probe 全部只能进入一个集合
同一个 event 下的相关 market 尽量放在同一个集合
同一天的高波动窗口不能拆散到训练和测试两边
```

否则同一个盘口状态的相邻订单可能一部分进训练、一部分进测试，导致验收结果虚高。

建议同时生成：

```text
按 probe bootstrap
按 market bootstrap
按 event bootstrap
```

的置信区间。

# 十、校准模型真正需要拟合什么

## 1. Latency Model

当前 paper engine 不应继续依赖单一固定延迟。

拟合：

```text
decision → send
send → ack
send → matched
```

然后按订单环境输出：

```text
p50 latency
p90 latency
p95 latency
p99 latency
```

保守 paper PnL 应优先使用：

```text
p90/p95 到达延迟
```

而不是平均值。

---

## 2. Depth Survival / Haircut

模拟盘在 decision 或 estimated arrival 时看到的深度，不一定仍能被真实订单吃到。

可以定义：

```text
depth_survival_ratio =
    actual_filled_size
    /
    paper_eligible_visible_size
```

按这些变量拟合：

```text
book update intensity
order/depth ratio
spread
price region
delay class
book age
市场类别
短期价格移动
```

最终产生：

```text
effective_depth =
    displayed_depth × depth_haircut(features)
```

建议第一版采用保守分位数，而不是均值：

```text
depth_haircut = conditional p10/p20 survival ratio
```

---

## 3. Fill Outcome Model

分类：

```text
REJECT
NO_FILL
PARTIAL
FULL
DELAYED
UNKNOWN
```

对 FOK 来说，最重要的不是整体准确率，而是：

```text
false_positive_full_fill
```

因为模拟盘认为全部成交、实盘却没有成交，会系统性虚高策略收益。

---

## 4. Fee Model

费用原则上不应靠统计拟合，而应：

```text
根据 market-specific fee 参数精确计算
再用实际 trade fee 做一致性验证
```

应保存：

```text
feesEnabled
fee parameter snapshot
fee schedule version
trade fee_rate_bps
paper predicted fee
actual fee
rounding residual
```

---

## 5. Calibration Domain

校准通过后，不应声明：

```text
所有 Polymarket taker 模拟都已可信
```

而应声明类似：

```text
model_version: taker-cal-v1

validated_domain:
    order_types: [FAK, FOK]
    delay_types: [NONE]
    order_to_depth_ratio: <= 0.50
    book_quality: REDUNDANT
    max_book_age_ms: 500
    spread_ticks: <= 3
    price_range: [0.10, 0.90]
```

超出范围的订单标记：

```text
EXTRAPOLATED
LOW_CONFIDENCE
UNCALIBRATED
```

# 十一、建议的 Go/No-Go 指标

下面是工程上的初始建议门槛，不是 Polymarket 官方标准。最终应根据你的目标下单规模收紧。

| 指标                             |               建议门槛 |
| ------------------------------ | -----------------: |
| unsafe real order              |                  0 |
| 无法解释的真实订单                      |                  0 |
| calibratable probe 数据完整率       |               100% |
| 真实账户账本重建差异                     |  0，允许 venue 最小舍入单位 |
| FOK false-positive full fill   |                  0 |
| 无延迟高流动性 fill-class accuracy    |               ≥99% |
| 全体 holdout fill-class accuracy |               ≥97% |
| VWAP error median              |        0～0.25 tick |
| VWAP error p95                 |            ≤1 tick |
| filled-size relative error p95 | ≤1%，或 venue 最小数量单位 |
| fee error                      |          ≤费用最小舍入单位 |
| User WS 丢失但无法通过 REST 恢复        |                  0 |
| UNKNOWN outcome                |                  0 |
| 连续漂移监控                         |     至少覆盖多个交易日和多个类别 |

即便 300 笔 FOK 中 false-positive 为 0，也不能说真实错误率等于 0。用简单的 “rule of three” 粗略理解，0/300 只能说明 95% 置信上界大约在 1% 左右。因此高风险或大金额使用场景仍需持续积累样本。

# 十三、必须做的故障注入测试

校准之前至少测试：

| 故障                         | 预期                                        |
| -------------------------- | ----------------------------------------- |
| User WS 断开                 | REST 能补全订单和交易                             |
| HTTP 返回丢失                  | 先按 order hash 查询，禁止盲目重下                   |
| 相同 WS event 重复             | 幂等去重                                      |
| 提交后进程崩溃                    | 重启后从 signed order/hash 恢复并 reconciliation |
| REST 暂时超时                  | probe 保持 UNKNOWN，不计入样本                    |
| trade 进入 RETRYING          | 不记最终真实账本                                  |
| trade 最终 FAILED            | 回滚/修正真实确认账本                               |
| matching engine 返回 425     | 标记 maintenance，不算模型错误                     |
| post-only/cancel-only mode | taker probe 不提交                           |
| book 在 submit 前变 stale     | preflight 二次门禁阻止提交                        |
| kill switch 触发             | 停止新订单并检查所有 open order                     |

Polymarket 在 matching engine 重启期间会返回 HTTP 425，重启后还有约两分钟 post-only 模式；cancel-only/post-only 期间不能盲目重试原 taker order。([Polymarket Documentation][11])

对于网络超时，正确流程是：

```text
不知道提交是否成功
→ 不签一笔新订单直接重发
→ 按预计算 order hash/orderID 查询
→ 查 user WS
→ 查 GET order / GET trades
→ 确认不存在后才考虑新的 probe attempt
```

# 十六、maker 仍然放在下一阶段

Taker Gate 通过之后，才进入：

```text
Sprint 6：Maker Queue Calibration
```

因为 L2 Market-By-Price 只展示价位聚合数量，看不到真实 FIFO 位置。HftBacktest 因此提供保守的 RiskAverseQueueModel 和概率 queue model；这说明 maker fill 必须被视为概率问题，不能把盘口数量下降直接当成自己的成交。([HftBacktest][1])

Maker 阶段需要新的真实 probe：

```text
post-only GTC/GTD
固定价位 resting
记录 queue_ahead
记录后续 trade evidence
真实 partial/full/no-fill
记录 cancel latency
```

Maker 指标也不同：

```text
Brier score
fill probability calibration curve
false-positive maker fill
time-to-fill error
partial-size error
cancel-before-fill error
```

# 最终执行顺序

你现在最具体的下一步是：

```text
1. 冻结当前 taker shadow model。
2. 完成 live adapter、User WS、REST、链上和账户对账闭环。
3. 完成风险门禁和 kill switch。
4. 连续跑 50～100 次完整 no-submit。
5. 在人工确认账户及金额边界后，跑 10～20 笔机械 probe。
6. 机械 probe 全部通过后，再跑 100～300 笔分层样本。
7. 拟合 latency、depth survival 和 fill correction。
8. 用按 market/event 隔离的 holdout 验收。
9. 只把校准覆盖范围内的 PnL 标记为可信。
10. 最后再开始 maker resting-order 和 queue calibration。
```

所以，从专业模拟盘建设角度看，**你已经完成了“能模拟成交”，下一步必须证明“模拟成交和真实成交之间的误差是多少、在哪些条件下误差可控”。只有这个 Calibration Gate 通过，模拟 PnL 才能从工程输出升级为可用于策略判断的研究证据。**
